Merge, rebase e conflitos

Branches separam o trabalho; merge e rebase juntam de novo. Entenda as formas de juntar e perca o medo de conflito.

A regra de ouro do merge

O git merge X traz as mudanças da branch X para a branch em que você está. Então primeiro você vai para quem vai receber, depois chama quem vai entrar:

# quero levar a feature para a main:
git switch main          # 1. vá para quem RECEBE
git merge feature/login  # 2. chame quem ENTRA

Dependendo de como as branches andaram, o Git junta de um jeito ou de outro.

Fast-forward: só avançar a etiqueta

Se a main não mudou desde que a branch foi criada, não há nada para combinar. O Git só empurra a etiqueta main para frente.

Merge de três vias: quando as duas andaram

Se a main também recebeu commits, o histórico se dividiu. O Git compara três versões: o ancestral comum (onde as branches se separaram) e as duas pontas. Então cria um commit de merge, que tem dois pais.

Quer o commit de merge mesmo quando daria fast-forward (para deixar visível que existiu uma branch)? Use git merge --no-ff feature. É o que o botão de merge do GitHub faz por padrão.

Rebase: refazer a branch em cima da outra

O rebase é outra forma de trazer as novidades da main. Em vez de criar um commit de merge, ele copia os seus commits para depois do último commit da main, como se você tivesse começado a branch agora.

Nunca faça rebase de commits que outras pessoas já têm

Como o rebase cria commits novos, quem já baixou os antigos fica com um histórico diferente do seu. Use rebase só em commits que estão apenas no seu computador ou na sua branch pessoal. Na dúvida, use merge.

Merge, rebase ou squash?

No GitHub, ao integrar um pull request, você escolhe entre três botões:

OpçãoO que aconteceQuando usar
Create a merge commitMantém todos os commits da branch e cria um commit de merge.Padrão seguro. Mostra quando cada branch entrou.
Squash and mergeJunta todos os commits da branch em um commit novo na main.Branches com muitos commits do tipo “ajuste”, “agora vai”.
Rebase and mergeCopia os commits da branch para a ponta da main, sem commit de merge.Equipes que preferem histórico linear.

Conflitos: quando o Git precisa da sua decisão

O Git junta sozinho mudanças em arquivos diferentes, ou em partes diferentes do mesmo arquivo. O conflito acontece quando as duas branches mudaram as mesmas linhas de jeitos diferentes. O Git não tem como saber qual está certa, então para e pergunta.

Conflito não é erro

Não quebrou nada e nada foi perdido. É o Git pedindo para você escolher. Respire e siga os passos.

Como o conflito aparece

git merge feature/titulo
Auto-merging index.html
CONFLICT (content): Merge conflict in index.html
Automatic merge failed; fix conflicts and then commit the result.

Dentro do arquivo, o Git marca o trecho com as duas versões:

<<<<<<< HEAD
<h1>Bem-vindo à loja</h1>
=======
<h1>Loja do Campus</h1>
>>>>>>> feature/titulo
<<<<<<< HEAD
Começa a sua versão (a da branch em que você está).
=======
Divide as duas versões.
>>>>>>> feature/titulo
Termina a versão que está chegando.

Resolvendo passo a passo

  1. Veja quais arquivos estão em conflito 
    git status
Unmerged paths:
        both modified:   index.html
  2. Edite o arquivo e deixe só a versão final

    Pode ser uma das duas, uma mistura ou algo novo. Apague as três linhas de marcação.

    <h1>Bem-vindo à Loja do Campus</h1>
  3. Teste. Abra o site, rode o programa: o resultado precisa funcionar, não só compilar.
  4. Marque como resolvido e conclua o merge 
    git add index.html
git commit
# o Git já sugere a mensagem "Merge branch 'feature/titulo'"

Mudou de ideia no meio? git merge --abort desfaz a tentativa e volta tudo ao estado anterior. No rebase, o equivalente é git rebase --abort; para seguir depois de resolver, git add e git rebase --continue.

No VS Code é mais fácil

O VS Code destaca os conflitos com cores e mostra botões acima de cada um:

  • Accept Current Change: fica com a sua versão (HEAD).
  • Accept Incoming Change: fica com a versão que está chegando.
  • Accept Both Changes: mantém as duas, uma depois da outra.
  • Compare Changes: mostra lado a lado.

Para casos maiores, clique em Resolve in Merge Editor: ele abre três painéis (sua versão, a que chega e o resultado). Depois de resolver, salve, clique em + no arquivo (o git add) e faça o commit pelo painel de Source Control.

Como ter menos conflitos

  • Atualize sua branch com frequência (git pull na main e merge dela na sua branch).
  • Branches curtas: quanto mais tempo separada, mais diferente fica.
  • Combine com a equipe quem mexe em qual arquivo.
  • Use o mesmo formatador de código (Prettier, Black…) para evitar conflitos de espaços e aspas.

Cherry-pick: pegar só um commit

Às vezes você quer só uma correção específica de outra branch, sem trazer o resto. O cherry-pick copia um commit para onde você está.
