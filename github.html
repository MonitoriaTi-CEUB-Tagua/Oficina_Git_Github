Colaborando no GitHub

O Git guarda o histórico; o GitHub organiza as pessoas em volta dele. Aqui está o que você precisa para trabalhar em equipe e mostrar seus projetos.

Um tour pelo repositório

IssuesLista de tarefas, bugs e ideias. Cada issue tem número (#12), responsável e etiquetas.

Atalho escondido

Em qualquer repositório, aperte a tecla . (ponto). Abre o github.dev, um VS Code no navegador, onde dá para editar e fazer commits sem instalar nada.

Criando um repositório

  1. Clique em New (botão + no topo → New repository).
  2. Dê um nome curto, sem espaços: loja-campus, trabalho-poo.
  3. Escolha a visibilidade. Public: qualquer pessoa vê (bom para portfólio). Private: só quem você convidar.
  4. README, .gitignore e licença. Marque se vai começar pelo GitHub e clonar depois. Deixe tudo desmarcado se for enviar um projeto que já existe no seu computador (senão os históricos não batem).

Colaborador ou fork?

Depende de você ter permissão para escrever no repositório:

Colaborador

Para a equipe do trabalho. O dono do repositório convida em Settings → Collaborators. Todos clonam o mesmo repositório, criam branches nele e abrem pull requests para a main.

Fork

Para contribuir com projetos de outras pessoas, como open source. O botão Fork cria uma cópia do repositório na sua conta. Você trabalha na sua cópia e abre um pull request para o original.

# 1. clique em Fork no GitHub e clone a SUA cópia
git clone https://github.com/voce/projeto.git
cd projeto

# 2. aponte também para o repositório original, chamado de upstream
git remote add upstream https://github.com/dono/projeto.git

# 3. para atualizar sua cópia com o original
git fetch upstream
git switch main
git merge upstream/main
git push

Pull request: a proposta de mudança

Um pull request (PR) é um pedido: “por favor, junte a minha branch na main”. Ele reúne a conversa, a revisão, os testes automáticos e o botão de merge num lugar só. Abrir um PR não junta nada: o merge só acontece quando alguém aprova e clica.

  1. Envie sua branch 
    git push -u origin feature/carrinho
  2. Abra o PR

    O GitHub mostra uma faixa amarela Compare & pull request. Confira o destino: base é quem recebe (main), compare é a sua branch.

  3. Descreva

    O que mudou, por que e como testar. Se ainda não estiver pronto, crie como Draft.

  4. Revisão

    Peça revisão a um colega (Reviewers). Para responder aos comentários, faça novos commits na mesma branch e dê git push: o PR se atualiza sozinho.

  5. Merge

    Aprovado, clique em Merge pull request. Depois apague a branch no próprio GitHub e atualize sua main local com git pull.

## Issue relacionada
Closes #12

Escrever Closes #12 liga o PR à issue 12 e fecha a issue automaticamente quando o PR entra na main.

Como revisar o código de um colega

  • Abra a aba Files changed e leia o diff. Clique no + ao lado de uma linha para comentar.
  • Use Suggest changes para propor o código exato; o autor aceita com um clique.
  • No fim, Review changes: Comment (só comentários), Approve (aprovado) ou Request changes (precisa ajustar).
  • Comente o código, não a pessoa. “Esse loop pode ser trocado por um map?” funciona melhor que “isso está errado”.

Issues: organizando o trabalho

Uma issue descreve uma tarefa ou um problema. Use para dividir o trabalho da equipe: cada pessoa pega uma issue, cria uma branch e abre um PR que a fecha.

README do perfil

Crie um repositório com o mesmo nome do seu usuário (ex.: anasouza/anasouza). O README dele aparece no topo do seu perfil: ótimo para se apresentar a recrutadores.

GitHub Pages: publique um site de graça

Sites estáticos (HTML, CSS e JavaScript) podem ser publicados direto do repositório. Este guia, por exemplo, é publicado assim.

  1. Deixe o index.html na raiz do repositório (ou numa pasta /docs).
  2. Abra Settings → Pages.
  3. Em Source, escolha Deploy from a branch, selecione main e a pasta / (root), e salve.
  4. Espere um ou dois minutos. O endereço aparece no topo da página: https://seu-usuario.github.io/nome-do-repo/.

A cada push na main, o site é atualizado. Em repositórios gratuitos, o Pages exige que o repositório seja público.

GitHub Actions: automação a cada push

Actions roda tarefas automaticamente em servidores do GitHub: testes, verificação de estilo, publicação. Você descreve o que fazer num arquivo YAML dentro de .github/workflows/:

name: Testes
on: [push, pull_request]

jobs:
  testar:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install -r requirements.txt
      - run: pytest

O resultado aparece em cada pull request como ✓ ou ✗. Se falhar, clique em Details para ler o log.

Combinados para a equipe

  • Ninguém faz commit direto na main: tudo entra por pull request. Dá para obrigar em Settings → Rules (ou Branches), exigindo revisão antes do merge.
  • Uma tarefa por branch, PRs pequenos.
  • Todo PR é revisado por pelo menos uma pessoa.
  • Quem abre o PR resolve os conflitos dele.
  • Um CONTRIBUTING.md explica como rodar o projeto e os combinados. Modelos de issue e de PR ficam na pasta .github/.
  • Senhas, tokens e chaves nunca vão para o repositório, nem em repositório privado.
