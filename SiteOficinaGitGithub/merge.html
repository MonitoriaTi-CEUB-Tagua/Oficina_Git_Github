Merge, pull requests e conflitos

Una mudanças com revisão. Entenda o destino do merge e resolva conflitos preservando o comportamento esperado.

Merge entra na branch atual

Para trazer uma feature para main, primeiro entre na main. O argumento de merge é a branch que você quer integrar.

terminal
git switch main
git pull --ff-only
git merge feature/menu
# Confira o resultado e teste o projeto
git push origin main
Dois caminhos: o exemplo faz merge local. Em equipe, normalmente você envia a feature e integra pelo pull request no GitHub. Se a main exigir revisão, não tente enviar diretamente para ela.

Pull request: proposta e revisão

Um pull request (PR) apresenta mudanças de uma branch para outra, permitindo comentários, testes e aprovação. Criá-lo não faz o merge automaticamente.

  1. Envie sua branch: git push -u origin feature/menu.
  2. No GitHub, abra Pull requests → New pull request.
  3. Confira base (destino, por exemplo main) e compare (sua feature). Em forks, confira também os repositórios de origem e destino.
  4. Explique o problema, a solução e os testes. Use Draft se ainda não estiver pronto para revisão.
  5. Em Files changed, revise o diff. Solicite revisão, responda comentários e envie novos commits na mesma branch para atualizar o PR.
  6. Quando revisões e verificações exigidas passarem, faça o merge pelo método permitido. Depois atualize sua main local.
modelo de descrição de PR
## O que mudou
Adiciona o menu de navegacao responsivo.

## Como testar
1. Abra index.html.
2. Reduza a largura da janela.
3. Navegue usando apenas o teclado.

## Issue relacionada
Closes #12

Closes #12 vincula a issue e pode fechá-la automaticamente quando o PR é integrado à branch padrão.

Três formas de integrar

MétodoO que aconteceEscolha comum
Merge commitPreserva os commits da branch e cria um commit com dois pais quando há divergência.Manter a história de integração visível.
Squash and mergeReúne as alterações do PR em um único novo commit no destino.PR com muitos commits intermediários.
Rebase and mergeReaplica os commits sobre o destino sem commit de merge; os identificadores mudam.Histórico linear, quando a equipe adota esse fluxo.

No Git local, fast-forward apenas avança a referência da branch: acontece quando o destino não divergiu da origem. Não cria um novo commit de merge.

Resolva um conflito com calma

Conflitos aparecem quando o Git não consegue combinar mudanças automaticamente, como edições concorrentes na mesma região de um arquivo. Isso exige uma decisão sobre o conteúdo final.

terminal
git switch feature/menu
git fetch origin
git merge origin/main

Se a integração parar por conflito, use git status para localizar os arquivos. Um conflito de texto pode aparecer assim:

index.html — conflito
<<<<<<< HEAD
<h1>Guia de Git</h1>
=======
<h1>Git e GitHub</h1>
>>>>>>> origin/main

Neste merge, o primeiro trecho é da sua feature atual; o segundo é da main buscada. Edite o arquivo para o resultado correto e remova todos os marcadores:

index.html — resolvido
<h1>Guia de Git e GitHub</h1>
terminal
git add index.html
git diff --staged
# Execute os testes ou confira a pagina
git commit -m "merge: integra main e resolve titulo"
git push
Não escolha um lado cegamente. A resolução pode combinar as duas intenções. “Sem conflito” também não garante que o programa funciona; teste o comportamento.

Precisa cancelar a tentativa?

terminal
git merge --abort

Use enquanto um merge está em andamento para tentar voltar ao estado anterior. Começar com a área de trabalho limpa evita problemas na recuperação de alterações prévias. Não é um comando para desfazer um merge já concluído.
