Prática Capítulo 4

Branches: linhas paralelas

Uma branch deixa você experimentar à vontade sem tocar na versão que funciona. É o recurso que torna o trabalho em equipe possível.

Por que usar branches

  • A main sempre funciona. O que está pela metade fica na sua branch até ficar pronto.
  • Várias tarefas ao mesmo tempo. Uma branch para o login, outra para corrigir o rodapé. Você troca entre elas em um segundo.
  • Várias pessoas ao mesmo tempo. Cada pessoa trabalha na sua branch e as mudanças se juntam depois, com revisão.
  • Experimentar sem medo. Não deu certo? Apague a branch e pronto.

Analogia

É como salvar o jogo antes de uma fase difícil e testar outro caminho num slot separado. Se der certo, você continua dali; se não, volta ao save principal.

Criando e trocando de branch

Lembre do capítulo de teoria: a branch é uma etiqueta, e o HEAD diz em qual etiqueta você está. Acompanhe:

Comandos de branch

ComandoO que faz
git branchLista as branches locais (-a inclui as do GitHub).
git switch -c nomeCria a branch a partir de onde você está e entra nela.
git switch nomeTroca para uma branch que já existe.
git switch -Volta para a branch anterior (como o “voltar” do controle remoto).
git branch -m novo-nomeRenomeia a branch atual.
git branch -d nomeApaga uma branch que já foi integrada. O Git recusa se houver commits que se perderiam.
git branch -D nomeApaga mesmo assim. Use só se tiver certeza.

switch ou checkout?

O git checkout é o comando antigo e faz muitas coisas (trocar de branch, restaurar arquivo, ir para um commit). Em 2019 o Git criou o git switch (trocar de branch) e o git restore (restaurar arquivos), mais fáceis de entender. Os dois funcionam; tutoriais antigos usam git checkout -b nome, que equivale a git switch -c nome.

Trocar de branch com alterações pendentes

Se você editou arquivos e tenta trocar de branch, duas coisas podem acontecer:

  • As alterações vão junto para a outra branch, quando não conflitam. Isso confunde: parece que você editou a branch errada.
  • O Git recusa: error: Your local changes to the following files would be overwritten by checkout.

Antes de trocar, faça um commit. Se o trabalho ainda não está bom para commit, guarde na stash, uma gaveta temporária:

# guarda as alterações e deixa a pasta limpa
git stash -m "login pela metade"

# agora pode trocar à vontade
git switch fix/rodape
# ... resolve o que precisava ...
git switch feature/login

# devolve as alterações guardadas
git stash pop

# ver o que tem na gaveta
git stash list

Detached HEAD: quando o HEAD não está numa branch

Você pode pedir para ver um commit antigo com git checkout B (ou git switch --detach B). O HEAD passa a apontar direto para o commit, e não para uma branch. É o tal detached HEAD.

Regra prática

Se o git status disser HEAD detached at … e você quiser fazer mudanças, crie uma branch antes: git switch -c nome.

Estratégias de equipe

Uma estratégia de branches é o combinado da equipe sobre quais branches existem e como o trabalho chega na main.

GitHub Flow (recomendado para começar)

Só existe uma branch permanente, a main. Cada tarefa vira uma branch curta, que volta para a main por um pull request revisado. Simples e suficiente para a maioria dos projetos de faculdade e de equipes pequenas.

Git Flow

Um modelo mais formal, com uma develop permanente e branches específicas para preparar versões (release) e corrigir produção (hotfix). Aparece em empresas com versões numeradas e datas de lançamento. Para projetos pequenos, costuma ser burocracia demais.

Qual usar na faculdade?

GitHub Flow. Uma branch por tarefa, pull request para a main, revisão de pelo menos um colega. Se o professor ou a empresa pedirem outro modelo, os conceitos são os mesmos.
