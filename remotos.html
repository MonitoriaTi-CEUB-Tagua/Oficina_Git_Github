Prática Capítulo 6

Remotos: push, pull e fetch

Até aqui, tudo ficou no seu computador. Agora você vai conectar o repositório ao GitHub e trocar commits com outras pessoas.

O que é um remoto

Um remoto é um endereço de outra cópia do repositório, normalmente no GitHub. Por convenção, o principal se chama origin.

git remote -v
origin  https://github.com/voce/meu-site.git (fetch)
origin  https://github.com/voce/meu-site.git (push)

O Git também guarda a última posição conhecida de cada branch do remoto: origin/main, origin/feature… Nos grafos, ela aparece como uma etiqueta tracejada. Ela só se atualiza quando você conversa com o GitHub (fetch, pull ou push).

Dois jeitos de começar

Use o clone: ele baixa o histórico inteiro e já configura o origin. No GitHub, clique no botão verde Code e copie o endereço.

git clone https://github.com/usuario/projeto.git
cd projeto

O clone cria uma pasta com o nome do repositório. Não rode git init depois: o clone já é um repositório.

  1. No GitHub, clique em New repository. Dê um nome e não marque README, .gitignore nem licença (o repositório precisa nascer vazio).
  2. No terminal, dentro da pasta do projeto (que já tem commits):
git remote add origin https://github.com/voce/meu-site.git
git branch -M main
git push -u origin main

O git branch -M main garante que a branch se chama main (projetos antigos podem usar master).

push: enviar seus commits

fetch e pull: receber o que os outros enviaram

git fetch
Só baixa os commits novos e atualiza as etiquetas origin/…. Sua branch e seus arquivos não mudam. É seguro rodar a qualquer momento.
git pull
Baixa e junta: é um git fetch seguido de um git merge origin/main (ou rebase, se configurado). Muda seus arquivos.

Push rejeitado: o erro mais comum de quem trabalha em grupo

Se alguém enviou commits para a mesma branch depois do seu último pull, o GitHub recusa o seu push. Ele não deixa você sobrescrever o trabalho do colega.

Algumas equipes preferem git pull --rebase, que reaplica o seu commit depois do commit do colega em vez de criar um merge:

Não use git push --force para “resolver”

O --force obriga o GitHub a aceitar o seu histórico e apaga os commits dos colegas que você não tinha. Só use na sua própria branch, sabendo o que está fazendo. Mesmo assim, prefira --force-with-lease, que recusa se houver commits que você não viu.

Upstream: a ligação entre branch local e remota

O upstream diz para onde o git push e o git pull sem argumentos devem ir. Ele é configurado pelo -u no primeiro push, ou automaticamente quando você troca para uma branch que só existe no GitHub:

# cria a branch local ligada à origin/feature/menu
git fetch
git switch feature/menu

# ver as ligações e se você está à frente/atrás
git branch -vv
* main          a1b2c3d [origin/main] adiciona estilo
  feature/menu  9f8e7d6 [origin/feature/menu: ahead 2] menu responsivo

A rotina de quem trabalha em equipe

  1. Atualize a main 
    git switch main
git pull
  2. Crie a branch da tarefa 
    git switch -c feature/minha-tarefa
  3. Trabalhe com commits pequenos 
    git add .
git commit -m "adiciona validação do formulário"
  4. Envie e abra um pull request 
    git push -u origin feature/minha-tarefa

    O próprio terminal mostra um link para criar o pull request no GitHub.

  5. Depois do merge, limpe 
    git switch main
git pull
git branch -d feature/minha-tarefa
