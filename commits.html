Prática Capítulo 3

Commits: salvando versões

O ciclo que você vai repetir centenas de vezes: editar, escolher o que entra, registrar. Aqui você cria seu primeiro repositório do zero.

O ciclo básico

  1. Edite os arquivos no editor e salve.
  2. Confira o que mudou com git status e git diff.
  3. Escolha o que vai para o commit com git add.
  4. Registre com git commit -m "mensagem".

Mão na massa: seu primeiro repositório

Abra o terminal (Git Bash no Windows) e siga junto. Os textos em cinza são o que o Git responde.

  1. Crie a pasta do projeto e transforme em repositório 
    mkdir meu-site
cd meu-site
git init
Initialized empty Git repository in .../meu-site/.git/
  2. Crie um arquivo

    Abra a pasta no VS Code (code .), crie um index.html com qualquer conteúdo e salve. Ou pelo terminal:

    echo "<h1>Meu site</h1>" > index.html
  3. Pergunte ao Git o que ele vê 
    git status
On branch main
No commits yet
Untracked files:
  (use "git add <file>..." to include in what will be committed)
        index.html

    O arquivo é untracked: o Git sabe que ele existe, mas ainda não acompanha.

  4. Coloque no stage 
    git add index.html
git status
Changes to be committed:
        new file:   index.html
  5. Faça o commit 
    git commit -m "cria página inicial"
[main (root-commit) 4e1b7a2] cria página inicial
 1 file changed, 1 insertion(+)
 create mode 100644 index.html
  6. Mude algo e repita

    Edite o index.html, crie um style.css e faça mais um commit. Depois veja o histórico:

    git add .
git commit -m "adiciona estilo"
git log --oneline
9c3d0f1 (HEAD -> main) adiciona estilo
4e1b7a2 cria página inicial

Lendo o git status

O git status é o comando mais útil para quem está começando: rode sempre que estiver em dúvida. Ele ainda sugere o próximo comando.

Se aparecerSignificaPróximo passo
Untracked filesArquivos novos, nunca adicionados.git add arquivo
Changes not staged for commitArquivos conhecidos que mudaram.git add arquivo ou git restore arquivo para descartar
Changes to be committedMudanças prontas no stage.git commit -m "..."
nothing to commit, working tree cleanTudo igual ao último commit.Trabalhar ou enviar com git push
Your branch is ahead of 'origin/main' by 2 commitsVocê tem commits que o GitHub não tem.git push

Formas de usar o git add

ComandoO que coloca no stage
git add index.htmlSó esse arquivo.
git add css/Tudo dentro da pasta.
git add .Tudo o que mudou na pasta atual e subpastas, inclusive arquivos novos.
git add -pPergunta trecho por trecho se você quer incluir. Ótimo para separar mudanças em commits diferentes.
git commit -am "msg"Atalho: adiciona arquivos já rastreados e faz o commit. Arquivos novos ficam de fora.

Cuidado com o git add .

Ele adiciona tudo, inclusive o que não deveria (senhas, arquivos gigantes, pastas de dependências). Rode git status antes e mantenha um .gitignore no projeto.

Vendo o histórico e as diferenças

# histórico resumido, uma linha por commit
git log --oneline

# histórico desenhado como grafo, com todas as branches
git log --oneline --graph --all

# o que mudou num commit específico
git show 9c3d0f1

# o que mudou na pasta e ainda não está no stage
git diff

# o que está no stage e vai entrar no próximo commit
git diff --staged

Para sair de telas longas (como a do git log), aperte q.

Boas mensagens de commit

A mensagem é para a pessoa que vai ler o histórico daqui a seis meses (provavelmente você). Regras simples:

  • Diga o que mudou de forma específica: “corrige cálculo do frete”, não “ajustes”.
  • Comece com um verbo no presente: adiciona, corrige, remove, atualiza.
  • Primeira linha curta, até uns 50 caracteres. Se precisar explicar o porquê, rode git commit sem -m e escreva um parágrafo depois de uma linha em branco.

Evite

update
ajustes
agora vai
asdfgh
mudanças no código

Prefira

adiciona formulário de contato
corrige menu cortado no celular
remove dependência não usada
atualiza instruções do README

Conventional Commits

Muitas equipes usam um prefixo que indica o tipo da mudança. Não é obrigatório, mas deixa o histórico fácil de ler:

PrefixoQuando usarExemplo
feat:Funcionalidade novafeat: adiciona busca de produtos
fix:Correção de bugfix: corrige login com e-mail maiúsculo
docs:Só documentaçãodocs: explica como rodar o projeto
style:Formatação, sem mudar comportamentostyle: aplica formatador
refactor:Reorganiza código sem mudar o que ele fazrefactor: separa validação em função
test:Testestest: cobre cálculo de desconto
chore:Manutenção (configs, dependências)chore: atualiza dependências

Qual o tamanho certo de um commit?

Uma mudança lógica por commit. Se a mensagem precisa de um “e” (“adiciona login e muda cor do rodapé”), provavelmente são dois commits. Commits pequenos são fáceis de revisar, de entender e de desfazer sem levar junto o que estava certo.

E faça commits com frequência. Terminou uma parte que funciona? Commit. Ele é seu ponto de salvamento.

.gitignore: o que não deve ir para o histórico

Crie um arquivo chamado .gitignore na raiz do projeto. Cada linha é um padrão de arquivo ou pasta que o Git deve fingir que não existe.

# dependências (são reinstaladas com npm install / pip install)
node_modules/
.venv/
venv/

# segredos: NUNCA versione
.env
*.key

# arquivos gerados
dist/
build/
__pycache__/
*.log

# lixo do sistema e de editores
.DS_Store
Thumbs.db
.idea/
  • O GitHub tem modelos prontos para cada linguagem, e oferece um deles ao criar um repositório.
  • O .gitignore só vale para arquivos ainda não rastreados. Se um arquivo já entrou num commit, veja como tirar.
  • O próprio .gitignore deve ser versionado, para valer para toda a equipe.

Desfazendo coisas antes do push

Enquanto os commits estão só no seu computador, dá para corrigir quase tudo com segurança:

SituaçãoComando
Quero descartar o que mudei num arquivo (voltar ao último commit)git restore index.html
Coloquei no stage sem querergit restore --staged index.html
Errei a mensagem do último commitgit commit --amend -m "mensagem certa"
Esqueci um arquivo no último commitgit add arquivo e git commit --amend --no-edit
Quero desfazer o último commit, mantendo as alteraçõesgit reset --soft HEAD~1

Repare no que o --amend faz de verdade: ele não edita o commit, cria um novo e abandona o antigo.

Para mais casos (commit já enviado, arquivo apagado, commit na branch errada), consulte Problemas e soluções.
