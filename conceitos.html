Teoria Capítulo 1

Como o Git funciona

Antes de decorar comandos, entenda o modelo mental. Com ele, quase todo comando do Git passa a fazer sentido sozinho.

Ao final você vai saber:

  • o que é versionamento e por que todo projeto precisa dele;
  • o que existe dentro de um commit e o que é o hash;
  • por onde um arquivo passa até virar histórico (as três áreas);
  • por que criar uma branch é instantâneo, e o que é o HEAD.

O problema que o Git resolve

Se você já entregou um trabalho, provavelmente já viu uma pasta assim:

trabalho-final.docx
trabalho-final-v2.docx
trabalho-final-v2-corrigido.docx
trabalho-final-v3-AGORA-VAI.docx
trabalho-final-v3-AGORA-VAI-revisao-do-joao.docx

Funciona até a primeira dúvida: qual é a versão certa? O que mudou entre a v2 e a v3? Quem apagou aquele parágrafo? Como juntar o que o João e a Maria editaram ao mesmo tempo?

Um sistema de controle de versão responde essas perguntas. Ele guarda o histórico de um projeto: cada versão, quem fez, quando e por quê. Você volta a qualquer ponto, compara versões e junta o trabalho de várias pessoas. O Git é o sistema de controle de versão mais usado no mundo.

Centralizado ou distribuído

Centralizado (SVN, CVS)

Existe um servidor com o histórico. Cada pessoa tem só a versão atual dos arquivos e precisa de conexão para salvar uma versão nova ou ver o passado.

Se o servidor cair, ninguém trabalha.

Distribuído (Git)

Cada computador tem uma cópia completa do histórico. Você faz commits, cria branches e consulta o passado sem internet.

O GitHub é só mais uma cópia, que a equipe combinou de usar como ponto de encontro.

Commit: uma foto do projeto inteiro

Um commit é uma versão salva do projeto. Pense nele como uma foto de todos os arquivos naquele momento. Arquivos que não mudaram não são copiados de novo: o Git reaproveita a versão anterior, por isso o histórico fica leve.

Cada commit guarda:

  • a foto dos arquivos (o conteúdo de cada um);
  • autor e data, vindos da sua configuração user.name e user.email;
  • uma mensagem explicando o que mudou;
  • o pai: o commit que veio antes. É isso que forma a corrente do histórico.

Você pode ver tudo isso com um comando:

git cat-file -p HEAD
tree 8f2b1c0e4a7d9f3b2c5e6a1d0f9e8c7b6a5d4c3b
parent 3f9a2c1d8e7b6a5f4c3d2e1f0a9b8c7d6e5f4a3b
author Ana Souza <ana@exemplo.com> 1729425600 -0300
committer Ana Souza <ana@exemplo.com> 1729425600 -0300

O hash: a impressão digital do commit

Cada commit recebe um identificador como 3f9a2c1d8e7b6a5f4c3d2e1f0a9b8c7d6e5f4a3b. Esse hash é calculado a partir de tudo o que o commit contém: arquivos, autor, data, mensagem e o hash do pai.

  • Mudou uma vírgula? O hash muda. Por isso o histórico não pode ser alterado sem que ninguém perceba.
  • Como o hash do pai entra na conta, mudar um commit antigo muda o hash de todos os que vêm depois.
  • No dia a dia você usa só os primeiros 7 caracteres: git show 3f9a2c1.

Por que isso importa

Quando um comando “reescreve o histórico” (rebase, commit --amend, reset), ele cria commits novos, com hashes novos. Os antigos não mudam: ficam para trás. Guarde essa ideia; ela explica vários problemas mais à frente.

As três áreas

Este é o conceito que mais confunde no começo. Um arquivo passa por três lugares até virar histórico:

Pasta de trabalho
Os arquivos que você vê e edita no editor. Salvar com Ctrl+S muda só aqui.
Staging (área de preparação)
Uma lista do que vai entrar no próximo commit. Você escolhe com git add.
Repositório
O histórico de commits, guardado na pasta oculta .git. Entra aqui com git commit.

Experimente: edite arquivos, escolha o que vai para o stage clicando neles e faça commits.

        Analogia

        A pasta de trabalho é a mesa onde você monta as coisas. O staging é a caixa onde você coloca o que vai mandar. O commit fecha a caixa, cola uma etiqueta com a descrição e guarda no arquivo.

        Por que existe o staging? Para você fazer commits organizados. Se mexeu no menu e corrigiu um erro de digitação no rodapé, dá para fazer dois commits separados, cada um com sua mensagem, mesmo tendo editado tudo de uma vez.

        Branch é só uma etiqueta

        Aqui está o segredo que torna o Git tão rápido: uma branch não é uma cópia da pasta. Ela é só uma etiqueta com nome que aponta para um commit. Criar uma branch é criar uma etiqueta nova; custa praticamente nada.

        O HEAD é outra etiqueta especial: ele indica em qual branch você está. Quando você faz um commit, a branch do HEAD avança para o commit novo e as outras ficam paradas.

        Você vai se aprofundar nisso no capítulo de branches.

        Local e remoto

        Tudo até aqui acontece no seu computador. O repositório remoto é uma cópia em um servidor (GitHub, GitLab…) que a equipe usa para trocar commits. O Git só conversa com o remoto quando você pede:

        Salvar, commit e push são coisas diferentes

        Salvar grava o arquivo no disco. Commit registra uma versão no histórico do seu computador. Push envia seus commits para o GitHub. Se você fez commit e não fez push, seus colegas não veem nada.

        Por dentro da pasta .git

        Quando você roda git init, o Git cria uma pasta oculta .git. Todo o histórico mora nela. Vale espiar uma vez para perceber que não há mágica, só arquivos:

        ls .git
HEAD  config  description  hooks/  index  info/  objects/  refs/

cat .git/HEAD
ref: refs/heads/main

cat .git/refs/heads/main
3f9a2c1d8e7b6a5f4c3d2e1f0a9b8c7d6e5f4a3b
        • HEAD é um arquivo de texto dizendo em qual branch você está.
        • refs/heads/main é a branch main: um arquivo com o hash de um commit. É literalmente uma etiqueta.
        • objects/ guarda o conteúdo, comprimido e nomeado pelo hash. São três tipos: blob (conteúdo de um arquivo), tree (uma pasta: lista de nomes apontando para blobs e outras trees) e commit.
        • index é o staging.

        Não mexa na pasta .git na mão

        Apagar a pasta .git apaga todo o histórico local; os arquivos continuam, mas viram uma pasta comum. Também não crie um repositório dentro de outro (um git init dentro de uma pasta que já está num repositório).

        Resumo

        • Git guarda o histórico de uma pasta; GitHub hospeda esse histórico na internet.
        • Um commit é uma foto completa do projeto, com autor, mensagem e um ponteiro para o pai.
        • O hash identifica o commit e muda se qualquer coisa nele mudar.
        • Arquivos passam pela pasta de trabalho, pelo staging (git add) e entram no repositório (git commit).
        • Branch é uma etiqueta que aponta para um commit; HEAD diz em qual branch você está.
        • Só push, pull, fetch e clone conversam com o remoto.
